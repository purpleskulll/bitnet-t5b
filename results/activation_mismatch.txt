THE FILE DOES NOT SETTLE IT, which is the part that matters. The checkpoint's
GGUF carries 24 metadata keys. Read directly from the header here:

  general.architecture = bitnet-b1.58, general.name = bitnet2b, vocab_size,
  context_length, embedding_length, block_count, feed_forward_length,
  rope.dimension_count, attention.head_count, attention.head_count_kv,
  attention.layer_norm_rms_epsilon, rope.freq_base, general.file_type,
  general.quantization_version, and ten tokenizer.* keys.

There is NO activation key of any kind -- no match for activ, relu, silu, act_
or gelu anywhere in the key set. So the loader's per-architecture default is the
only thing choosing the activation, and nothing in the file contradicts it or
confirms it.

WHAT THIS DOES NOT TOUCH, and the reason is structural rather than hopeful:
both arms run the SAME graph. Bit-identity, the six-significant-figure
perplexity agreement, the density figures and every rate in this repository are
comparisons between two formats evaluated under one loader, so a wrong
activation cancels exactly. The paper already declined to report an absolute
perplexity as a result; this is a second, concrete reason for that refusal
beside the tokenizer-metadata one it already gave.

SETTLED, 2026-09-13. One token of diff, then llama-perplexity on both arms,
same forty chunks, same session. Full log: results/activation_run_2026-09-13.log

                        i2_s                     t5b
  LLM_FFN_SILU      96.8243 +/- 3.55673      96.8243 +/- 3.55673
  LLM_FFN_RELU_SQR  16.7482 +/- 0.50521      16.7482 +/- 0.50521

A factor of 5.78. The activation WAS the cause. The 96.8243 this repository has
quoted throughout describes a mis-built graph, not this checkpoint.

THE NEGATIVE CONTROL HELD, and it is the reason this changes nothing else. The
two arms agree to six significant figures under BOTH activations. They have
always run the same graph, so a wrong activation cancels exactly in the
comparison; had they diverged here, something other than the activation would
have been wrong. Every rate, every density figure and the bit-identity result
are comparisons under one loader and are untouched.

The graph was restored afterwards and the tree rebuilt, so the working copy is
back on LLM_FFN_SILU -- verified by grep, not assumed.

Note that it is not a discovery: microsoft/BitNet#588 reports the same
mismatch. What is unpublished is this checkpoint's perplexity under this
harness, which is exactly the number the paper declines to quote.

A SECOND PAYOFF IF IT HOLDS, recorded so the reason is not lost. A squared
rectifier produces EXACTLY zero, not a small number, so the gate's zero
structure would be exact and skippable without a threshold or a predictor.
That is the only large remaining speed axis the improvement sweep found, and it
is gated entirely on this one-token experiment. Its ceiling, computed from the
in-situ decomposition, is 25.47 % of ternary MACs, i.e. about 11 % of a token --
and the published sparsity figure it would lean on (67.5 %) is a 7B number from
BitNet a4.8 (arXiv:2411.04965), whose own table runs 21.8 % to 84.2 % across
scales. Extrapolating it to a 2.4B checkpoint is not justified; the per-layer
fraction has to be measured, and it falls out of the same rebuild for free.
